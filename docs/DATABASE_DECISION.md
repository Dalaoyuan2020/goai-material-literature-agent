# 明日数据库决策清单

## 先回答当前是不是数据库

当前是“可查询的本地文件知识库”，不是正式数据库。

现有持久化数据包括：

- `knowledge/edges.csv`：核心 DOI 证据边；
- `knowledge/edges_matkg.csv`：MatKG 聚合弱证据边；
- `outputs/pipeline_report.json`：知识管线产物；
- `outputs/search_runs/*.json`：候选搜索运行；
- `outputs/llm_calls/*.json`：LLM 决策审计。

Node 后端中的任务、作业和报告使用内存 `Map`，重启服务后丢失。因此从软件工程意义看，还没有达到正式数据库层。

## 科研人员需要数据库解决什么问题

建议数据库只围绕实际科研问题建设：

1. **证据追溯**：某条材料关系来自哪篇论文、哪段原文、证据等级是什么；
2. **材料实体归一**：别名、化学式、掺杂表达和同一材料的不同写法可以合并；
3. **组合检索**：按材料家族、关系类型、年份、DOI、证据等级联合查询；
4. **候选与证据分离**：已验证核心事实、弱证据和模型候选不可混在一起；
5. **实验闭环**：科研人员可记录候选的待核验、已否定、文献支持、实验支持状态；
6. **可复现运行**：记录一次搜索使用的数据版本、参数、模型、审计和输出；
7. **团队协作**：多人批注、审核和导出时不会依赖个人机器上的 JSON 文件。

## 明日必须确认的问题

### 用户与场景

- 第一批用户是谁：材料信息学研究者、实验材料研究者，还是文献情报人员？
- 高频动作是查证据、找相似材料、管理候选，还是跑批量分析？
- 单机个人使用还是课题组多人共享？
- 数据规模是一千条、十万条，还是百万条关系？

### 数据边界

- 哪些记录允许编辑，哪些是不可变的原始证据？
- 是否保存 PDF、全文和向量，还是只保存元数据与摘录？
- DOI、材料、关系、运行、候选、人工评价分别需要哪些字段？
- 候选转为核心事实需要什么人工审核流程？

### 技术选型

- **本地单机 MVP**：优先 SQLite，部署最简单，适合当前 Electron/Web 本地应用；
- **团队共享服务**：优先 PostgreSQL，适合权限、并发、审计和备份；
- **图关系探索**：先用关系库表达边；只有复杂多跳查询成为核心需求后，再评估 Neo4j 等图数据库；
- 向量检索可以后续使用 SQLite/PostgreSQL 扩展，不建议一开始拆出独立向量数据库。

## 建议的最小数据模型

- `materials`：规范材料实体及别名；
- `papers`：DOI、题名、年份和来源；
- `evidence_edges`：材料 A、材料 B、关系、证据等级、论文和摘录；
- `hypotheses`：未验证候选、分数、生成依据和人工状态；
- `runs`：工作流、版本、参数、状态和产物；
- `audit_events`：模型调用、人工审核和数据变更记录。

## 明日的成功标准

会议结束时应得到一页明确结论：目标科研用户、三个最高频任务、必须持久化的数据、数据规模、单机或团队部署方式，以及 SQLite/PostgreSQL 的选择。没有这些结论前，不建议直接开始数据库迁移。
